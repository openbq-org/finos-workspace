# Plugin permissions and commands

A permission is something that a widget's manifest asks for and an admin approves. A command is the call that the module makes with `experimental.invoke` to use a permission. The host checks every command against the widget's effective permissions before it carries the command out.

A widget should ask only for the permissions that it uses. An organization can remove permissions for its users, so the module reads the `capabilities` trait before it calls a command and degrades gracefully when a permission is missing.

## Permissions

The list is generated from the permissions that the backend accepts in a manifest. A manifest that asks for <PluginList of="permissionsLater" /> is blocked, because this host does not implement it yet.

## Commands

The call `experimental.invoke(name, msg, { buffers, signal, timeout })` returns a promise that resolves to `[value, DataView[]]`. The call times out after <PluginValue of="limits.COMMAND_TIMEOUT_MS" unit="ms" /> unless the module passes a `timeout` or a `signal`. Buffers are `ArrayBuffer` objects or typed arrays.

| Command | Permission | Message | Behavior and limits |
|---|---|---|---|
| `core:asset:read` | `core:default`, which every widget has | `{ path }`, where the path names a file under `assets/` | The call resolves to `{ path, size }` and passes the file as the one buffer. The host checks the file against the approved version. Another path is an `invalid_args` error, and a file that the version does not contain is an `out_of_scope` error. A large file needs a longer `timeout`. |
| `core:ui:notify` | `core:ui:notify` | `{ level, text }`, where `level` is one of <PluginValue of="limits.NOTIFY_LEVELS" or /> | The host shows the text as plain text of at most <PluginValue of="limits.MAX_NOTIFY_LENGTH" /> characters, labelled with the plugin's name. It lets through <PluginValue of="limits.NOTIFY_RATE.perSecond" /> notices per second, with bursts of up to <PluginValue of="limits.NOTIFY_RATE.burst" />. |
| `core:ui:open-link` | `core:ui:open-link` | `{ url }` | The host opens only links with the schemes <PluginValue of="limits.LINK_PROTOCOLS" />, and only after the user confirms. |
| `core:dashboard:add-widget` | `core:dashboard:add-widget` | `{ widget, data, name }`, where `widget` is the id of a widget of the same plugin that declares an `artifact`, and `name` is optional | The host adds that widget to the dashboard, standalone and without parameters, holding `data`, as when the user adds an artifact from the chat. The data must satisfy the artifact's schema and may be at most <PluginValue of="limits.MAX_ADDED_WIDGET_BYTES" unit="bytes" />. The host takes the call only within <PluginValue of="limits.ACTION_GRANT_MS" unit="ms" /> after the user picks one of the widget's [actions](package-and-manifest.mdx#actions), once for each pick, and otherwise it is an `out_of_scope` error. On a shared or locked dashboard, or when the dashboard does not take the widget, it is `unavailable`, and the pick is used up. The data is plain JSON: no `NaN`, infinite numbers, sparse arrays or objects other than plain objects. The call resolves to `{ instanceId }`, the new widget's `meta.instanceId`. Without a `name`, the widget is named after the widget that added it, followed by "(static)". The new widget records which widget it was copied from and when, which the AI agent sees, and the user can rename it and change its description in its Settings. |
| `core:clipboard:write` | `core:clipboard:write` | `{ text }` | The text may be at most <PluginValue of="limits.MAX_CLIPBOARD_BYTES" unit="bytes" />. The command rejects with `unavailable` when the browser refuses the write, for example when no action of the user in the widget came before it. |
| `core:download:save` | `core:download:save` | `{ filename, mime }`, with the file as the first buffer | The file may be at most <PluginValue of="limits.maxExportBytes" unit="bytes" />, and the host cleans the file name. |
| `core:proxy:call` | `core:proxy:call` | `{ id, args }` | The call runs a proxy that the widget declares, as [Plugin proxies and secrets](proxies.mdx) describes, and it resolves to the response body. It counts against the server call rate of <PluginValue of="limits.SERVER_CALL_RATE.perSecond" /> calls per second, with bursts of up to <PluginValue of="limits.SERVER_CALL_RATE.burst" />. |
| `core:backend:call` | `core:backend:call` | `{ route, args }` | The call runs a route of the plugin's backend that the widget declares, as [Plugin backends](backends.mdx) describes, and it resolves to the route's JSON. It counts against the same server call rate as `core:proxy:call`. |
| `core:presets:list` | `core:presets` | `{}` | The call resolves to `{ presets }`, where each preset is `{ id, name, scope, isDefault }` and `scope` is `user` or `org`. It lists the user's own presets of this widget first and then the organization's, as [Presets](module-contract.mdx#presets) describes. |
| `core:presets:apply` | `core:presets` | `{ id }` | The host writes the preset's settings and state to this card, checked as a write to `config` and to `state` is, and the call resolves to `{}`. An id that is not one of the listed presets is an `out_of_scope` error. |
| `core:presets:save` | `core:presets` | `{ name, isDefault }`, where `isDefault` is optional | The host saves the card's current settings and state as a new preset of the user and resolves to `{ id }`. The name is trimmed and has 1 to <PluginValue of="limits.MAX_PRESET_NAME" /> characters, or the call is an `invalid_args` error. When the user already keeps as many presets of the widget as the organization allows, the call is a `too_large` error with the server's message. The host lets through <PluginValue of="limits.PRESET_SAVE_RATE.perSecond" /> saves per second, with bursts of up to <PluginValue of="limits.PRESET_SAVE_RATE.burst" />. |

The preset commands are `unavailable` on a shared dashboard.

When the host refuses a call, the promise rejects with an `Error` whose `name` is one of <PluginList of="commandErrors" or />. At most <PluginValue of="limits.MAX_PENDING_COMMANDS" /> calls may wait for an answer at the same time.

The messages that carry these calls between the frame and the host are on [Plugin frame protocol](../protocols/plugin-frame.mdx).

## Exports

A module that returns exports from `initialize` offers the members <PluginList of="exportMembers" />. The permissions `core:export:provide` and `core:copilot:context` allow the host to call them. The function `exportOptions` returns a list of export options, at most <PluginValue of="limits.MAX_EXPORT_OPTIONS" /> of them, and each option has these fields:

<PluginExportOption />

The host gives `exportOptions` <PluginValue of="limits.EXPORT_TIMEOUTS_MS.exportOptions" unit="ms" />, `exportData` <PluginValue of="limits.EXPORT_TIMEOUTS_MS.exportData" unit="ms" /> and `copilotContext` <PluginValue of="limits.EXPORT_TIMEOUTS_MS.copilotContext" unit="ms" />. An export may be at most <PluginValue of="limits.maxExportBytes" unit="bytes" />, and the result of `copilotContext` may be at most <PluginValue of="limits.MAX_COPILOT_CONTEXT_BYTES" unit="bytes" />.
